# ADR-0005: 品牌色与交互色统一到青绿单色相轴（修订 D4 / UI-06 / 浅色层 accent 跨主题一致）

- 状态：**已定案（2026-10-03）**
- 日期：2026-10-03
- 决策者：产品负责人裁决（方向批准 + 六批实施），开发团队实施
- 上游：UI 视觉设计报告（v1.2 二轮评审修订版，§0.3 决策摘要 / §5.1）——**该报告已归档**
- 落地：UI 视觉执行计划 v1.0（开发计划，执行真源）——**已归档**
- 修订对象：
  1. **D4**（UI 设计改进计划 §7，**已归档**）：「青绿 = 品牌识别 / 蓝 `--accent` = 功能交互」双色分工；
  2. **UI-06**（同上）：「`.devtools-tab.active` 从 `--accent` 改成 `--brand`，同为标签激活态应统一」；
  3. **浅色层裁决**（`shell/src/style.css:216`，改造前）：「accent/danger 等语义色保持深色值，确保强调色跨主题一致」。

## 背景

Pylume 的观感问题是**身份问题**而非能力问题（方案 §1）：工程底座 token 化彻底，但界面看起来像"没有贴牌的 VS Code"。实测三条：

1. **真正承载功能语义的是蓝色 `--accent`，不是品牌青绿**：`--accent` 82 处（含 `--on-accent` 13 / `--accent-soft` 15 / `--accent-faint` 4 / `--accent-hover` 4，交互色家族共 118 处），而 `--brand` 只有 24 处 —— 前者是后者的 3.4 倍。用户看到的是"蓝的选中/焦点/链接 + 蓝紫的欢迎页 logo + 青绿的活动标签/运行按钮"，三个色系、两种语言。
2. **D4 的双色分工长期失衡且方向错位**：它把"品牌识别"分给出现 24 次的青绿，把"功能交互"分给出现 82 次的蓝。UI-06 曾试图把 1 处 devtools tab 拉向品牌色，方向恰好相反（只改 1 处，没触及大头）。
3. **既有裁决阻止了浅色侧的修正**：`style.css:216` 明写"accent 跨主题一致"，使浅色主题无法为 accent 取更深的青绿（青绿在白底上必须更深才达 AA）。

另有一处硬约束（方案 §5.1 实测证明）：**accent 单值不可兼得** —— 它既是「描边/文字/焦点环」（需该色 on 画布 ≥4.5），又是「实心按钮底」（其上 13 处 `--on-accent` 白字需 ≥4.5）。实测白字 on `#2aa88f` 仅 2.96，而 `#1f8070` 作为画布文字仅 3.42 —— 两个角色数学上冲突。

## 决策

**青绿（色相约 165°）成为唯一色相轴，同时承载品牌与交互；accent 按角色拆三个 token。**

```
--brand-1..5         单一色相、明度分级的高亮→极深阶梯
--accent             = --brand-3（#2aa88f）：≤S3 面上的文字 / 图标 / 描边 / 焦点环
--accent-emphasis    = --brand-2（#4ec9b0）：≥S4 / hover / control-hover / selected 四个亮面上的 accent 文字与图标
--accent-fill        = --brand-4（#1f8070）：实心按钮底，其上放 --on-accent 白字（4.79 ✅）
```

配套取值范围：

- **深色**：`--accent` / `--accent-hover` / `--accent-soft` / `--accent-faint` / `--link` / `--link-hover` / `--link-border` / `--diff-hunk` / `--debug-frame-active` / `--welcome-glow` / `--brand-gradient` 全部收进青绿（11 个取值点，深色 8 + 浅色 3，逐个实算达标）。
- **浅色**：新增 accent 族覆盖（`--accent: #0e7261`，白底 5.84 / 白字 5.84，一值两用，故 `--accent-fill: var(--accent)`）；`--accent-emphasis: #0b6350`；`--selected` 由蓝 `#d6ebff` 换青绿 `#d3efeb`；`--link` / `--link-hover` / `--diff-hunk` 同步青绿化。
- **语义色不动**：`--ok` / `--danger` / `--warn` / `--meta` 与 Git/diff 状态色不属于品牌色轴，保持原值（其中 `--ok` 本身已是青绿，属巧合，不作依赖）。
- **语法色 `--syntax-*` 明确排除在本次之外**：它们是代码调色板，必须与 Monaco 主题 `rules` 同批改（批 4），提前改会让编辑器与外壳脱色数个批次。

**九面门禁**（配套约束，非可选）：`--accent` 作为文字/图标色必须在 S0–S4 + `--hover` / `--control-hover` / `--selected` / `--tab-inactive-bg` 九个面上合规；实测 `#2aa88f` 在 S4（4.11）/ hover（4.42）/ control-hover（3.81）/ selected（3.63）四面跌破 4.5，故这四个面上的 accent 文字与图标一律走 `--accent-emphasis`（九面实测 5.27–9.32 全达标）。

## 备选方案

| 方案 | 评估 | 结论 |
|---|---|---|
| **维持 D4 双色分工**（青绿品牌 + 蓝交互） | 82 处蓝色构成用户实际看到的主色系，"品牌识别"沦为 24 处的点缀；三色系并存是"拼装感"的直接来源 | ❌ **推翻** |
| 只改 logo / 欢迎页渐变（v1.0 初始方向） | 归因错误：logo 只占 2 处，真正遗留是交互层；改 2 处不解决 82 处 | ❌ 否决（v1.1 评审纠正） |
| `--accent` 一值两用（不拆 fill / emphasis） | 白字 on 填充底 ≥4.5 与该色作为画布文字 ≥4.5 数学上不可兼得（§5.1 实测表）；勉强取中会两头不达标 | ❌ 否决 |
| `--accent-emphasis` 取 `#45c2ab`（更内敛） | 九面最低 4.88 也达标，但引入第 6 个品牌档位，与"减法"原则冲突 | ❌ 否决（采纳 `--brand-2` 复用现有档位） |
| 语法色一并与交互色同批青绿化 | `--syntax-*` 需与 Monaco `rules` 一一对应，提前改会让编辑器与外壳配色脱节数个批次 | ❌ 推迟到批 4 |
| **青绿单色相轴 + accent 三角色** | 改的是 token 定义而非 82 处调用点，成本常数级；同时消除色系分裂与"贴牌感" | ✅ **选定** |

## 后果

**正面**

- 交互层与品牌同源，色系从 3 支收敛到 1 支（+ 独立的代码调色板与语义色）；
- 改动成本常数级（token 定义 ≈20 行 + 审计脚本 + 单测），不触碰 82 处调用点；
- 九面门禁把"hover 行里的链接看不清"这类隐性缺陷变成可机检项。

**约束与代价**

- `--accent` 不再是"一个值走天下"，新增 `--accent-emphasis` / `--accent-fill` 两个角色；新增样式必须先判断落点面（≤S3 用 `--accent`；≥S4 / hover / control-hover / selected 用 `--accent-emphasis`；实心按钮底用 `--accent-fill`）。选择器级迁移在批 2b 完成，由门禁「四面 0 命中」守住；
- 浅色层从此有 accent 覆盖，第三条裁决失效 —— `style.css` 对应注释必须改写（注释考古纪律）；
- 蓝色残留只剩代码调色板（`--syntax-var` / `--syntax-boolean` 及其浅色值），批 4 统一；
- 品牌渐变由蓝紫改青绿后，欢迎页 logo 与 menubar 单色 logo 终于同源。

**验证**

- `tools/ui/audit_tokens.py`：单色相（色相差 ≤15°）、accent 面门禁、白字 on `--accent-fill`、浅色 `--fg-dim` 四档；
- `shell/src/__tests__/styleTokens.test.ts`（批 2a 起）：`style.css` ↔ `index.html` FOUC 块 ↔ `[data-theme="light"]` 覆盖层三方一致，批 4 扩为四方（加 Monaco 主题）；
- 基线截图 8 张（深/浅 × 编辑区/侧栏/终端/设置）逐批比对，不接受纯人工抽查。
