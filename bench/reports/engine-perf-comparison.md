# 静态引擎性能对比（撤销 basedpyright 推荐的决策依据）

> 日期：2026-09-28 · 性质：决策追溯文档（对应 Pydantic 支持计划 §1.1 / 阶段 3 落盘任务，该计划已归档）
> 数据来源：会话复现记录（2026-09-28，真实项目实测）——**非本文件落盘时重测**；复现方法见 §3。
> 结论用途：解释为何撤销「Pydantic 栈 → 推荐 basedpyright」（F0 裁决 B），pyrefly 回归唯一默认静态引擎。

---

## 1. 一页结论

basedpyright 的 Pydantic 正确性优势（4/6 覆盖，见 `pydantic-engine-probe.md`）是用「**多窗口秒级卡顿 + 大文件重**」换来的：

| 指标 | basedpyright | pyrefly | 差距 |
|---|---|---|---|
| 输入 `time.` 补全 warm avg（全量） | **4.7s** | 1.9s | ~2.5× |
| 输入 `time.` 补全 warm avg（增量后） | 1.8s | 1.9s | 追平但已付出首卡 |
| 多窗口 CPU 竞争放大 | 单窗 72ms → 双窗 120ms（+67%） | 几乎无放大 | 质变 |

**产品取舍**：单人自用 IDE，交互流畅性（补全延迟）优先于静态正确性缺口；Pydantic 缺口改由「显式化提示 + 自研语义层」补齐（见计划阶段 2/4），而非推荐用户切换引擎。

## 2. 测量环境（会话复现时）

- 项目：真实业务项目（`cli.py` 13783 行 + `nacos_client.py`）
- 场景：编辑器内连续输入 `time.` 触发成员补全，warm 状态取平均；双窗口 = 两个工作区同时开（两份引擎进程并行）
- 口径：warm avg = 索引就绪后连续多次取均值；单窗/双窗对比 = 同文件同位置补全的响应耗时

## 3. 复现方法

```powershell
# 1. 打开真实大文件项目（或任意 >1 万行 .py 的工作区）
# 2. 状态栏引擎 chip 切到 basedpyright，等索引就绪（状态 ready）
# 3. 编辑器输入 `time.` 触发补全，重复 5+ 次取平均（首次为全量 cold，后续为 warm）
# 4. 再开第二个窗口加载另一工作区，重复第 3 步（观察 CPU 竞争放大）
# 5. 切回 pyrefly 重复 3-4，对比
```

指标口径与产品一致：补全请求从键入到候选弹出的耗时（含引擎往返），不剥离 Monaco 渲染。
